## 1. Three corrections to 09-20. Read these before deploying.

### 1.1 The deploy order in 09-20 §5.2 is wrong

09-20 §5.2 says of the two deploys: *"Either order is safe — old carts carry
legacy stamps and resolve exactly as they do today."* **That is false, and
following it can undo the repair script.**

The new extension writes `exit_intent_holdout = "<decisionId>|<epochMs>"`. The
**currently deployed** server does:

```js
const aiDecisionId = (holdoutDecisionId && holdoutDecisionId !== 'true')
  ? holdoutDecisionId : null;
```

`"abc|1758…"` is not `'true'`, so it becomes the lookup key, `findFirst` misses,
and the handler falls through to its **create** path — re-inserting exactly the
duplicate `InterventionOutcome` rows `repair-duplicate-outcomes.mjs` just
folded. Same shape for `exit_intent_decision`. The new server's `readCartStamps`
parses both formats; the old one does not.

**`flyctl deploy` must come BEFORE `shopify app deploy`.** See §4.

### 1.2 The Enterprise promo guard is dead, not merely Pro-gated

09-19 §1.3 says the real guard is Enterprise-gated. It is also **never armed for
anyone.** `Promotion` rows have exactly one writer,
`webhooks.discounts.create.jsx`, and `discounts/create` is **not subscribed** in
`shopify.app.toml`. The table is empty for every shop on every plan, so
`db.promotion.findFirst` always returns null and `variant-engine`'s `duringPromo`
is permanently `false`.

So §1.3 was never "Pro has no guard" — **nobody had a working guard.** The new
detector rests entirely on the client-reported `promoInCart` signal.
Subscribing `discounts/create` (no re-auth; `write_discounts` already covers it)
plus a backfill for existing discounts is the successor item.

### 1.3 §1.1 was smaller than 09-19 claimed, and hybrid changes §1.3's shape

09-19 §1.1 was written without accounting for two things that already existed:
the `exitIntentThresholdOffer` sessionStorage stash that `cart-monitor.js`
monitors, and the document-level checkout interception in
`exit-intent-modal.js`, which already matched Dawn's `button[name="checkout"]`.
The qualify → check out → discount path therefore already worked on
Dawn-family themes. What was actually broken is in §2.4 below.

And on §1.3: **hybrid shops override `baseline` unconditionally** a few lines
after `selectBaseline` returns
(`baseline = hybridOfferAmount > 0 ? 'conversion_with_discount' : 'pure_reminder'`).
So no baseline-level guard can ever affect a hybrid shop. See §3.2.

## 2. What shipped

### 2.1 §5.1 — the cross-store publish gate

`aggregate-gene-performance.js` gated on
`storeCount < minStores && totalImpressions < 100`, which skips only when BOTH
bars fail — i.e. it published whenever EITHER passed. One store with 100+
impressions published its **merchant-authored copy strings** and its **absolute
revenue dollars** at `sampleSize: 1`.

Now both bars must clear, through a shared `meetsPublishGate()`
(`app/utils/meta-learning-gate.js`).

**§5.1 is NOT closed by this, and the next handoff must not say it is.** §5's
envelope is k≥5 stores with *bounded per-store weight* and *no absolute
per-store revenue crossing a boundary*. What landed is k≥3, unbounded weight,
and `totalRevenue` / `avgProfitPerImpression` are still written as summed
absolute dollars. Three stores at 98/1/1 impressions clear both bars and the
published revenue figure is ~98% one store's — the same subtraction attack §5
item 3 flags at k=2.

What **is** closed: the k=1 leak, and with it the merchant-copy leak, because a
headline unique to one merchant can never reach `storeCount >= 3`.

Note this is also **stricter than before for cluster rows** (`minStores` 2),
which now need ≥100 pooled impressions too. Cluster priors will populate later
than the old code implied. Do not "fix" that back.

### 2.2 §5.2 — template priors

`template-priors.js` read `MetaLearningGene` with **no `sampleSize` gate** while
the other reader of the same table required ≥3 stores, so k=1 rows reached
another merchant's runtime sampling through that path alone. Both readers and
the writer now share `MIN_META_STORES`.

### 2.3 §5.6 — shop redaction reported clean while five tables survived

The live handler is `app/routes/webhooks.jsx` (`webhooks.shop.redact.jsx` exists
but nothing routes to it — the gap between them is now wider).

`VisitorTouch`, `VariantSegmentStat`, `EvolutionCursor` and `AdminAuditLog`
carry a `shopId` **string with no foreign key**, so Postgres raised nothing,
`db.shop.delete` succeeded, and the handler logged a clean success. This is the
exact failure shape its own header warns about, one class over. `VisitorTouch`
matters most: it holds the durable per-shopper `resparqVisitorId`.

`MetaLearningInsights` has no `shopId` column at all — `surface-arm.server.js`
and `discount-arm.server.js` encode it into `segment` as `${shopId}::`. Deleted
by **insightType AND prefix**, so genuinely global rows (generated copy, cluster
priors) are never swept up, and `archetype_performance_by_vertical` — which also
uses `::`, but with a vertical — is safe because of the insightType half.

`AdminAuditLog` was a judgement call, not a mechanical one: those are records of
*our* admin actions, and deleting them destroys our audit trail. Resolved toward
deletion because the handler's standard is "erasure means erasure." The
reasoning is in `redaction-scope.js` so nobody reverses it blind.

**One residual, deliberately not fixed.** `calibrate-propensity.js` writes
`storeIntercepts[shopId]` into the `data` JSON of a single **global**
`MetaLearningInsights` row. A per-shop fitted coefficient keyed by shop id
survives redaction. Fixing it needs a read-modify-write of the global row, which
risks the live propensity model for every shop. It is a regression coefficient
keyed by an internal UUID, not identifying data.

### 2.4 §1.1 — threshold stranding

Two independent causes.

**The unguarded stash.** `applyDiscountCode`'s `sessionStorage.setItem` was
bare. A throw unwound out of `checkThreshold` before `bannerShown` latched, so
the card was already on screen saying *"code X applied at checkout"* while
nothing had been stored and nothing would apply it — and the cart stamp still
credited us with the conversion. It now returns whether the stash landed, and
both the cart card and the mini-cart say *"use code X at checkout"* when it
didn't.

The reachable trigger is **not** a storage-blocked browser — `getActiveOffer`
would have returned null and we would never reach here — but **quota exhaustion
arriving mid-session**.

`bannerShown` is now latched **before** the two render calls, so a throw out of
a render cannot leave the 2s poll re-entering forever. The `removeItem` in the
drop-below branch is guarded for the same reason.

**The selector.** The interception matched `button[name="checkout"]` (Dawn) but
not `input[type=submit][name="checkout"]`, which is Debut, Brooklyn, Narrative
and most custom themes. On those, a shopper who earned a discount checked out
and paid full price. That is the bulk of the real §1.1 exposure.

Widening it made three latent problems reachable, each worse than the bug. All
three are closed — see §3.3.

### 2.5 §1.3 — the promo-stacking detector

`signals.hasPromoActive` was READ in two places and WRITTEN nowhere, so
`selectBaseline`'s "a promo is already running, do not stack" branch had **never
once executed**. `app/utils/promo-detect.js` is the missing writer.

**Detection only.** Flipping `combinesWith` is the wrong lever: not retroactive,
breaks free shipping, and it inverts the failure mode into one where Shopify
refuses to combine and **the shopper can pay more than they would have without
us**. Stacking costs the merchant margin; replacing costs the shopper money. The
comment at `discount-codes.js:126` documents a correct decision — the gap was
detection, not combination.

The asymmetry that made this safe to ship this week: a false positive serves a
reminder instead of an offer, the modal **still renders**, still stamps the
cart, and a **no-click conversion still credits**. No merchant-facing number can
go to zero in either direction.

## 3. Decisions likely to be second-guessed

### 3.1 Detection reads a client-supplied signal

`promoInCart` comes from the storefront and is forgeable. The forgery direction
is "claim a promo exists" → receive a reminder instead of a discount. No shopper
has an incentive to do that. Accepted.

### 3.2 Hybrid is carved out of the promo guard — but that is not why it is safe

`hasPromoActive` returns false for hybrid, matching the existing hybrid
carve-out on the Enterprise promo block (the merchant pinned the offer by hand
and Resparq honors it, spec §2 #1).

**Do not describe this as what makes the guard zero-delta for the live shop.**
It is already inert for hybrid because hybrid discards `selectBaseline`'s result
entirely (§1.3 above). With or without the carve-out, a hybrid shop's *served*
baseline is identical. The carve-out's only observable effect is keeping the
persisted `AIDecision.signals` JSON and the operator console's suppression
string honest — without it, both would claim a promo was the reason nothing was
spent while the pinned discount was served anyway.

**Consequence: §1.3 is structurally unfixable for hybrid through
`selectBaseline`.** A real hybrid guard has to act on the pinned offer itself —
suppress it, or reduce the amount. Not attempted. **The live shop is hybrid, so
§1.3's harm is still unfixed for the one merchant who could suffer it.**

### 3.3 The interception now reads the cart before redirecting

Three things the selector widening made reachable:

- **`/discount/<code>` REPLACES the cart's discount code.** A shopper who typed
  the merchant's `SUMMER20` and carried a stale code from a dismissed offer would
  have had theirs silently swapped for ours. The interception now reads
  `/cart.js` first and goes straight to `/checkout`, leaving their code alone,
  when the cart already carries a different **applicable** code **or an
  automatic discount**. Automatic discounts never appear in `discount_codes` —
  they are cart-level applications — and are the likeliest shape of the §1.3
  merchant promo, so missing them would have left this blind to its main case.
  `applicable !== false` is deliberate: a code Shopify is refusing to honour must
  not block ours, or the shopper gets no discount at all.
- **Pre-Dawn cart-form state.** On those themes the intercepted control is the
  submit button of the cart form, where `note`, `updates[]` and `attributes[]`
  are plain inputs only the native submit writes back. Cancelling that submit and
  navigating by GET would discard a gift note or an unsubmitted quantity edit —
  worse for a shopper than losing a discount, and breakage the widening would
  have *introduced*. The form is now posted to `/cart` first, **url-encoded and
  not multipart**, because urlencoded is what the browser itself would have sent
  and a quietly-rejected POST would have hidden the very state loss it prevents.
  Skipped when no such field exists, so Dawn pays no extra round trip.
- **The async window.** Cancelling the click means nothing visibly happens for up
  to 2.5s. An impatient second click used to read the already-cleared stash, skip
  `preventDefault`, and let the native submit race our redirect to checkout with
  no discount. A **deadline-based** latch keeps the second click inert — a
  deadline and not a boolean, because a boolean only cleared by the page
  unloading survives a bfcache restore, and a shopper pressing Back from checkout
  would find the checkout button permanently dead. Far worse than the
  double-click it guards.

Every path navigates: fetch rejecting, a non-JSON body, a throw in the handler,
an absent `discount_codes`, a request that never settles. The click is already
cancelled, so a path that failed to navigate would leave someone pressing
Checkout watching nothing happen. The timeout falls back to applying our code,
which is exactly what Dawn shoppers get today.

Still uncovered and uncoverable from here: **accelerated checkout** (Shop Pay,
PayPal, GPay), which bypasses the cart, and **form submission by Enter key**,
which fires no click.

## 4. Deploy order. This is not optional.

```
# 0. Snapshot, read-only. Do this first and keep the output.
node --env-file=.env scripts/dev/dashboard-preview.mjs <shop>
node --env-file=.env scripts/ops/promo-guard-preflight.mjs

# 1. The repair. Alone, at low traffic. Dry run first and READ IT.
node --env-file=.env scripts/ops/repair-duplicate-outcomes.mjs
node --env-file=.env scripts/ops/repair-duplicate-outcomes.mjs --apply

# 2. Server + schema.
flyctl deploy

# 3. Webhooks + extension. STRICTLY AFTER step 2 — see §1.1.
shopify app deploy

# 4. A SEPARATE DAY, and nothing else in the push:
#    @@unique([shopId, aiDecisionId]) on InterventionOutcome.
#    Only if step 1 reported zero duplicate groups.

# 5. A separate day: item 4's columns.
```

Step 1 must precede step 3 specifically, not just step 4: if the extension
ships before the server, the old server re-creates the duplicates the repair
just folded and you have to run it again.

**Never combine a constraint-adding push with any other schema change.**
`prisma db push` runs at container boot with no `--accept-data-loss` and there
is no `release_command`. If `CREATE UNIQUE INDEX` throws 23505, `npm run setup`
exits non-zero and **the container never starts** — and you will not know whether
the other `ALTER TABLE` landed. One statement, one push, watch the boot.

### Before step 2 — confirm one thing

`scripts/ops/promo-guard-preflight.mjs` prints `Shop.mode` from the database.
**The runtime does not read that.** `ai-decision.jsx` derives `isHybrid` from the
`exit_intent.settings` **metafield**; `app.analytics.jsx` calls the metafield
"the serving source of truth" and aligns the DB row afterwards, so a failed
second write leaves the two disagreeing.

If the live shop's metafield says `ai` while `Shop.mode` says `hybrid`, the
promo guard **is not** inert for them. **Confirm the metafield in the Shopify
admin**, or accept that §1.3 is live for that shop.

### Verification that could not be done here

The local `.env` points at a **dev** database — one shop, zero impressions — so
nothing in §2.5 was validated against production data. And nothing in §2.4 is
testable by `npm test`: `tests/**` cannot import the extension assets, which are
IIFEs with no exports.

Before trusting §2.4, on a Dawn theme and a pre-Dawn theme:
1. Qualify a threshold offer, check out via the theme's own button, confirm the
   discount lands.
2. Repeat with the merchant's own code already in the cart — confirm theirs
   survives and ours does not overwrite it.
3. Repeat with a gift note and an unsubmitted quantity edit — confirm both
   survive.
4. Repeat with storage blocked — confirm the card says "use code X at checkout"
   and never claims it is applied.

Per 09-20 §8, have the `exit-intent-modal.js` diff reviewed by someone who has
not read this document.

## 6. Traps — additions to 09-20 §8

- **`flyctl deploy` before `shopify app deploy`, always.** The old server
  mis-parses the new timestamped stamps and re-creates the duplicates the repair
  script folds. 09-20 §5.2's "either order is safe" is wrong.
- **`Shop.mode` is a mirror; the metafield is the serving source.** Any statement
  about what mode a shop is in, made from a DB query, is unverified.
- **Hybrid overrides `baseline` after `selectBaseline` returns.** Any
  baseline-level guard is inert for hybrid shops. Check for the override before
  concluding a guard works.
- **The `Promotion` table is empty for everyone**, because `discounts/create` is
  not subscribed. Any code reading it is dead code today.
- **A handoff claim that a §5 item is "closed" needs the envelope checked, not
  just the bug.** §5.1's one-character fix does not meet §5's k≥5 /
  bounded-weight / no-absolute-dollars bar, and it would have been easy to
  record it as done.
- **Extension assets cannot carry a `node:test`.** They are IIFEs with no
  exports and `tests/**` cannot import them. Any fix in `extensions/` ships on
  reasoning plus a manual checklist, which is exactly the profile 09-20 §8 warns
  about. Budget a storefront pass.
