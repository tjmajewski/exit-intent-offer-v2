## 2. The discount outage

### 2.1 Root cause

Commit `1276574` added three fields to **every** `discountCodeBasicCreate` site
so codes would discount the first billing cycle of a selling-plan item:
`customerGets.appliesOnSubscription`, `customerGets.appliesOnOneTimePurchase`
and `recurringCycleLimit: 1`.

Shopify rejects all three on a store with no selling plans:

```
applies_on_subscription field is not permitted without the shop using subscriptions.
applies_on_one_time_purchase field is not permitted without the shop using subscriptions.
recurring_cycle_limit field is not permitted without the shop using subscriptions.
```

They return as `userErrors`; the create site threw `Failed to create discount
code`; the endpoint's outer catch returned a 500. **The shopper saw no modal at
all** — not a modal without a discount.

The store sells wigs. It has no subscriptions and never will.

### 2.2 How it was found, because the technique is reusable

The write ordering in `apps.exit-intent.api.ai-decision.jsx` is what hid it:

```
recordImpression()        -> writes VariantImpression
...
createPercentageDiscount  -> THREW
db.discountOffer.create   -> never reached
db.aIDecision.create      -> never reached
outer catch               -> 500, no row anywhere
```

A crashed discount decision leaves an **impression row and no decision row**. The
failure is not merely unlogged, it is *absent*, and absence looks exactly like
"the engine chose not to spend".

Counting the gap exposed it, and the arithmetic was exact:

| | |
|---|---|
| `VariantImpression` rows (30d) | 132 |
| storefront `AIDecision` rows | 53 |
| gap | 79 |
| PERCENT_DISCOUNT 28 + FIXED_DISCOUNT 18 + THRESHOLD_DISCOUNT 38 | **84** |

The only archetypes that had **ever** rendered were `TRUST_REMINDER` (6) and
`SOFT_UPSELL` (3) — precisely the two that take the `type === 'no-discount'`
early return and never reach the mint.

**When a merchant-facing number looks wrong, diff the row counts of two tables
written at different points in the same request.** The gap names the failing
stage.

### 2.3 The fix (`547e6e3`)

`app/utils/discount-subscription-fields.js`. The three fields are added only when
the store actually has selling plans, checked once per shop per process with a
30-minute TTL. On any failure the check returns **false**, because the asymmetry
is brutal: a false negative costs a subscription shopper a discount on renewals;
a false positive costs **every** shopper their entire offer.

They can never take an offer down again even if that check is wrong: a rejection
naming any of the three triggers **one retry without them**, matched on the
GraphQL field path rather than the message text.

All four create sites now go through one `submitBasicCodeDiscount` helper. Four
hand-copied mutation literals is how three of them came to send rejected fields.

The helper also removed a masking bug: the old code read
`result.data.discountCodeBasicCreate.userErrors` without checking it, so a
top-level GraphQL error (which makes `data` null) surfaced as an opaque
`TypeError` instead of the real message. Thrown errors now carry the `userErrors`
text.

`createGenericDiscountCode` keeps `shopId` optional and therefore omits the
fields; `ensureSubscriptionEligibility` already backfills subscription
eligibility on the reuse path, so subscription stores are unaffected.

### 2.4 The second crash, newly reachable (`17edffd`)

`baseline.replace('with_discount', 'no_discount')` turned
`conversion_with_discount_fixed` into `conversion_no_discount_fixed`, which is
**not** one of the six pools in `gene-pools.js`. `getRandomGene` read
`.headlines` off undefined → 500 → no modal, no row. Same invisibility as §2.2.

Hidden behind the mint failure until now. With minting working it became the
remaining hole, and it was reachable: propensity clusters below 50, so most
visitors take `flatDiscountBaseline`, which splits them by `visitorId` hash
between the percentage and dollars-off pools; at aggression 8 the cold-start roll
withholds 20% of the time. **Roughly half of that 20% of eligible shoppers would
still have seen nothing.**

Replaced with an explicit map (`noDiscountCounterpart`), matching
`offerTypeForBaseline`. There is no dollars-denominated no-discount pool because
a no-discount offer has no denomination, and a `.replace` cannot know that.

### 2.5 An automatic discount no longer blocks the offer (`7eb5659`)

The checkout interception treated a cart-level **automatic** discount like a code
the shopper typed, and skipped applying ours. Reversed: only a typed code blocks
us.

`/discount/<code>` replaces the cart's discount **code** and does not touch
automatic discounts, so applying ours destroys nothing. A store-wide automatic
discount is the merchant's own baseline pricing; an incremental Resparq offer on
top is the product doing what it is sold to do. Blocking also contradicted the
promo guard, which ships **off** precisely because withholding offers from a live
merchant mid-trial is the riskier error.

Concretely: had Cami Wigs been running any automatic discount, that branch would
have withheld the code on **every checkout** and made the §2.3 fix look like it
changed nothing, with no error anywhere to explain it.

### 2.6 Verified

`scripts/ops/probe-discount-mint.mjs` calls the real module with the live token,
creates at most three codes and deletes every one. Against
`568e5d-75.myshopify.com` after the fix: percentage, fixed and threshold all
**SUCCESS**, all **deleted**. Confirmed present in the built bundle on the
container, not just in source.

## 3. Why a week passed — the pattern to design against

Three mechanisms had to line up, and all three are still live for other paths:

1. **A failure that writes nothing looks like a decision.** The outer catch
   returns a 500 and persists no row. Every other "no offer" path writes an
   `offerSuppression` record; this one writes nothing, so the console cannot
   distinguish "crashed" from "chose not to".
2. **Impressions are minted before the work that can fail.** Right for
   intent-to-treat, but it means a crash still produces a row that looks like
   ordinary traffic.
3. **Logs did not outlive the traffic.** At ~9 renders in 30 days, by the time
   anyone looks the buffer holds only health checks — and the health endpoint was
   firing continuously about the stalled evolution cron, which trained the eye to
   ignore it.

§6 item 2 is the fix for the class.

## 6. Next steps, by value to the platform

### 1. Watch the first real discount end to end — this week

Nothing else matters until one works. The entire client-side discount path has
never executed in production. Unproven:

- `{{amount}}` / `{{threshold}}` interpolation with a real non-zero amount, and
  the brand-safety copy clamp on top of it
- `decision.code` → `sessionStorage.exitIntentDiscount` → `/discount/<code>`
- `webhooks.orders.create.jsx` matching a real `EXIT20-…` / `EXIT10OFF-…` /
  `EXITSPEND100-…` code on the first redemption
- **Billing.** 09-20 §7 flags that the legacy path bills on `total_price`
  (includes tax) while the revenue card uses subtotal. With $0 ever discounted,
  `UsageCharge` has never fired for this shop. **Reconcile before the first
  redemption, not after.**

### 2. Make a silent failure impossible — the highest-leverage change here

A mint failure should degrade to the no-discount modal plus a recorded
`failure/discount_mint_failed` suppression, **not** a 500 that shows nothing and
writes nothing. That one change would have surfaced this outage on day one
instead of day seven, and it generalises to every throw between
`recordImpression` and `aIDecision.create`.

Pair it with a tripwire on the §2.2 gap: impressions minus decisions over 24h,
alerting above a small threshold. One query, and it detects this entire class.

### 3. Unstall the evolution cron

Stalled ~4.4 days with traffic present. The bandit is frozen, so "the engine
learns per store" is not currently true. The health check already detects it and
nobody was watching; route it somewhere that pages.

### 4. Stop `carts/update` polluting the decision corpus

359 of 412 rows are pre-decisions that never reach a shopper (§1.3), making every
raw count over `AIDecision` wrong. Either give them their own table, or require a
`source` filter in every reader, or stop writing them — they feed nothing today.

### 5. Record settings changes

`AdminAuditLog` has 0 rows, so an aggression change cannot be correlated with a
behaviour change. Cheap, and it is the first thing anyone wants when a merchant
says "it stopped working after I changed X".

### 6. Then the pre-existing backlog

09-19 §7 item 4 (`offeredAmount` / `offeredType` / `armSet`, its own schema
push), item 8 (inert machinery), §1.3 for hybrid (§7.3), and §5's remaining
compliance items — of which **no Shopify Customer Privacy API integration at

## 7. The compliance work that was today's original task

Landed in `09856bf`, all of it inert for the live shop.

### 7.1 §5.1 — the cross-store publish gate

`aggregate-gene-performance.js` gated on `storeCount < minStores &&
totalImpressions < 100`, which skips only when BOTH bars fail — it published
whenever EITHER passed. One store with 100+ impressions published its
merchant-authored copy strings and absolute revenue dollars at `sampleSize: 1`.
Both bars must clear now, via a shared `meetsPublishGate()`.

**§5.1 is NOT closed, and the next handoff must not say it is.** §5's envelope is
k≥5 with bounded per-store weight and no absolute per-store revenue crossing a
boundary. What landed is k≥3, unbounded weight, and `totalRevenue` still written.
What **is** closed is k=1, and with it the merchant-copy leak: a headline unique
to one merchant can never reach `storeCount >= 3`.

Also stricter than before for cluster rows (`minStores` 2), which now need ≥100
pooled impressions too. Do not "fix" that back.

### 7.2 §5.6 — shop redaction reported clean while five tables survived

`VisitorTouch` (durable per-shopper `resparqVisitorId`), `VariantSegmentStat`,
`EvolutionCursor` and `AdminAuditLog` carry a `shopId` **string with no foreign
key**, so Postgres raised nothing and `db.shop.delete` succeeded.
`MetaLearningInsights` has no `shopId` at all — two writers encode it into
`segment` as `${shopId}::`, now deleted by **insightType AND prefix** so global
rows are never swept up.

One residual, deliberately unfixed: `calibrate-propensity.js` writes
`storeIntercepts[shopId]` into a **global** row. Clearing it means a
read-modify-write of the live propensity model.

### 7.3 §1.3 — the promo guard, shipped OFF

`signals.hasPromoActive` was read in two places and written nowhere, so
`selectBaseline`'s "a promo is running, do not stack" branch had never executed.
The writer exists now, gated on `RESPARQ_PROMO_GUARD_ENABLED`, unset.

Off because the live shop is `mode=ai` (§1.2), so the hybrid carve-out does not
shield them, and 9 rendered impressions cannot say how often it would fire. **To
arm:** run `scripts/ops/promo-guard-preflight.mjs` on production; if it reports a
real verdict rather than INSUFFICIENT SAMPLE, set the flag. A flag and a restart,
no deploy. Only the exact string `'1'` counts.

Two limits recorded in the code: the `shopPromotion` limb is unreachable
(`discounts/create` is not subscribed, so `Promotion` is empty for every shop),
and **§1.3 is structurally unfixable for hybrid** because hybrid overrides
`baseline` unconditionally a few lines after `selectBaseline` returns. A real
hybrid guard must act on the pinned offer itself.

Also §5.2: `template-priors.js` read `MetaLearningGene` with no `sampleSize` gate
while the sibling reader required ≥3 stores. Both readers and the writer now
share `MIN_META_STORES`.

## 8. Traps — additions to 09-20 §8

- **`flyctl deploy` before `shopify app deploy`.** A stamp-format change is a
  two-sided contract; the server side lands first.
- **A local `.env` is the DEV database.** Its only shop is
  `exit-intent-test-2.myshopify.com`; the live shop is `568e5d-75`. Running an ops
  script locally and reporting it as production is how this document first
  concluded the live merchant was hybrid.
- **`Shop.mode` is a mirror; the `exit_intent.settings` metafield is the serving
  source.** They can drift.
- **Most `AIDecision` rows never reached a shopper.** Filter `source`, or the
  count is ~8x wrong.
- **A 500 in the decision endpoint writes nothing at all**, so a crash is
  indistinguishable from a deliberate no-offer. Until §6 item 2 lands, never read
  an absence of suppression records as an absence of failures.
- **Generic-code mode never calls the mint.** The dev store's 55 `DiscountOffer`
  rows were all `mode=generic`, which is why the unique-code path could be totally
  broken in production while local testing looked fine. Test the mode the merchant
  is actually on.
- **Extension assets cannot carry a `node:test`.** Anything in `extensions/` ships
  on reasoning plus a manual storefront pass.
