# Handoff — September 20, 2026

Continues `HANDOFF-2026-09-19.md`. That document is still the map: its §1–§6
describe faults that are almost all still open, and its §7 is still the order
of work. This one records what §2.5 actually became, what it changed about the
numbers on a merchant's screen, and the two things that need a human before the
next change on top of it.

Read 09-19 §2.5 first. Then this.

---

## 0. What changed, in one paragraph

The metrics contract is built and on `main` (`5d58ca0`, `e97513a`, `1b13d9a`).
Four numbers are defined, computed by pure tested functions, and one of them —
recovered revenue — is now attributable to a specific order, render-gated and
able to go down when a merchant refunds. The repo has a test framework for the
first time. Nothing has been deployed: the reversal webhooks are not registered
until someone runs `shopify app deploy`, and the `AttributedOrder` table is
empty until orders land after that. Until both happen, the merchant dashboard
reads exactly what it read on 09-19.

---

## 1. Stakes, because they changed the shape of every decision below

**There is one live shop. Their 14-day trial closes around 2026-09-26.**

Last 30 days: 381 AI decisions, 9 rendered impressions, 0 clicks,
2 conversions, $2,325 revenue, $0 discount given.

Two things follow from that, and both are load-bearing:

- **Both of their conversions are no-click.** Shoppers saw the modal, did not
  click it, and bought anyway. Any change that stops crediting that pattern
  takes their entire revenue number to zero. §3.2 below exists because of this.
- **Nine impressions a month means a single event is visible on the card.** One
  merchant self-test that leaks into the numbers moves the headline. §3.3
  exists because of this.

Do not evaluate a change to attribution against averages. Evaluate it against
those two facts.

## 2. What shipped

### 2.1 The four numbers

`app/utils/metrics-contract.js` — pure, no database, no clock beyond what the
caller passes, because §2.5 requires every one of these to carry a test with a
hand-computed expected value and a function that opens its own Prisma client
cannot have one.

| | | source |
|---|---|---|
| M1 | recovered revenue | `AttributedOrder`, arm = shown, rendered, refund-adjusted |
| M2 | discount cost | same rows, prorated against what survived a refund |
| M3 | verified lift | `InterventionOutcome` via `canonicalWhere`, ITT both arms |
| M4 | show rate | `canonicalWhere.shown` / (`shown` + `missed`) |

`getMetricsContract` (`app/utils/metrics-contract.server.js`) reads them.
It uses `canonicalWhere` from `shop-metrics.server.js` rather than private
count definitions — the codebase already owned the correct intent-to-treat
model and a second copy is how a sixth definition of "impressions" gets born.

### 2.2 Money

Revenue is `subtotal_price`: after discounts, before tax and shipping.
`total_price` carries both and a merchant reconciling one month finds the
difference immediately.

**It is deliberately not `current_subtotal_price`.** Shopify's `current_*`
family already reflects edits, returns and refunds — storing that as the
subtotal and then subtracting a reversal counts the refund twice. A $40 refund
on a $100 order reported $20. This was found in review, not in testing, and the
docstring in `order-money.js` had the semantics right while the code underneath
had them backwards. If you touch this file, read the header first.

### 2.3 Reversals

New handler, `app/routes/webhooks.orders.reversal.jsx`, on `orders/updated` and
`orders/cancelled`.

**`refunds/create` is deliberately not subscribed.** Its payload carries one
refund and neither subtotal field, so the reversal can only be *accumulated* —
and an additive total double-counts the moment Shopify redelivers, which it
will. The order payload lets every delivery recompute the same answer from
scratch. Idempotency by construction beats idempotency by bookkeeping.

`orders/updated` is the noisiest topic Shopify has, so there is a payload-only
guard before any database work.

### 2.4 Two cart stamps

Decision-time stamp for the shown arm (`exit_intent_shown_decision`), alongside
the existing render-time stamp. This closes 09-19 §2.2 on the write side: a
decided-but-never-rendered visitor used to leave no trace on the cart while
their decision still sat in the ITT denominator.

Stamps are written `<decisionId>|<epochMs>` and resolved by **recency**, not by
a fixed priority order. Shopify never clears a cart attribute and a decision is
minted per carted page load, so one cart routinely carries stamps from several
page loads at once.

One rule sits on top of recency, and it is the subject of §3.2.

### 2.5 One row per order

`AttributedOrder`, unique on `(shopId, orderId)`. Every counting bug in 09-19
§2 is the same shape: a second row created where an existing row should have
been updated. The database now refuses it rather than the call site
remembering to.

### 2.6 Fixed in passing, both pre-existing

- **Shop redaction was failing on any shop with AI decisions.**
  `InterventionOutcome` and `InterventionThreshold` were never deleted, so
  `db.shop.delete` threw a foreign-key violation and Shopify retried forever.
  The live handler is `app/routes/webhooks.jsx` — `webhooks.shop.redact.jsx`
  exists but nothing routes to it.
- **`getIncrementality`'s converted numerator was missing the `rendered`
  filter its denominator has**, which lets shownCVR exceed 100%.

## 3. The three decisions most likely to be second-guessed

Each of these was reversed at least once during review. Read the reasoning
before changing them back.

### 3.1 The unique index on `InterventionOutcome` is NOT in the schema

09-19 §2.1 left it open and §2.5 called for closing it. It is still open, on
purpose.

**Production applies schema with `prisma db push` at container boot**
(`package.json` `setup`, Dockerfile CMD `docker-start`). There is no
`release_command` in `fly.toml` and nothing runs `prisma migrate deploy` — the
43 folders in `prisma/migrations/` have never executed in production. A unique
index declared in `schema.prisma` would be issued by `db push` as a bare
`CREATE UNIQUE INDEX` against a table that still holds the §2.1 duplicate
pairs: 23505, `setup` exits non-zero, **the container never starts**.

That is a boot loop, not a failed migration. See §5.

### 3.2 A displayed modal outranks a later decision not to show one

Recency alone is wrong in one specific case, and it is this shop's only
conversion pattern. Shopper is shown a modal on a product page, dismisses it
without clicking, browses on, and the cart page mints a fresh decision that
skips. The skip stamp is newer. Resolved on recency the order reads as "we
showed this person nothing", takes the skip branch's early return, and writes
no `Conversion` row, no analytics revenue and no redemption flag.

So a render stamp beats a later skip stamp. Two bounds on it:

- **Only over skip.** A later *holdout* stamp still wins. Holdout is a
  measurement control and quietly moving a visitor into the treated group
  corrupts the only causal number in the product. The guard is on the winning
  arm, so a holdout winner is structurally unreachable by the override.
- **Bounded by the attribution window**, measured from the order date. Carts
  outlive the window they are counted over.

An earlier version of this let a render win outright. Do not go back to that —
it lets a stale render stamp from page A turn a page-C holdout visitor into a
treated one.

### 3.3 Test-mode renders must never stamp a real cart

`stampShownDecisionOnCart` always honoured `isResparqTestMode()`;
`renderStampAttributes()` did not. A merchant walking their own live storefront
left render evidence on a real cart, and once §3.2 shipped that evidence gets
resurrected into an attributed order. At nine impressions a month, one
self-test moves the headline.

All five stamp sites are now guarded — three in `exit-intent-modal.js`, the
recovery pill, and the cart banner in `cart-monitor.js`. **Guard around the
stamp, never with an early return**: the pill and cart-banner handlers do their
discount redirect *after* the stamp, and returning early breaks the merchant's
own test of the feature. That mistake was made and caught here.

## 4. What this does and does not change on a merchant's screen

Seven KPIs on `app/routes/app._index.jsx`, all from `getShopMetrics({days:30})`.
The admin console (`admin.shops.$shopId.jsx`) and `app.analytics.jsx` read the
same function, so all three reconcile by construction.

**Nothing is retroactive.** The deploy adds an empty table; it rewrites no rows.

Forward-looking:

| KPI | effect |
|---|---|
| Revenue From Offer Interactions | can increase — §3.2 recovering dropped sales |
| Orders Created | can increase, same mechanism |
| Success Rate | can increase; numerator is a subset of denominator, cannot exceed 100% |
| Avg Order | either direction |
| People Clicked | unchanged — no path here writes `clicked` |
| Click Rate | can dip; denominator grows, numerator does not |
| Times Shown | can increase where a conversion backfills a lost confirm-render |

**The headline card carries two bases and says which one it is on.**
`AttributedOrder` starts empty, so every existing shop is on the legacy basis
on day one. An earlier version blanked the card to "Measuring" in that state —
which takes a live merchant's revenue figure away overnight, a week before
their trial closes. The card shows the legacy number under the legacy wording
until the contract has data, then both switch together.

`scripts/dev/dashboard-preview.mjs` prints exactly what a given shop will
render, from the real modules, read-only. Use it before any deploy that touches
a merchant-facing number.

## 5. What needs a human before the next change

### 5.1 Run the repair, then add the index

```
node --env-file=.env scripts/ops/repair-duplicate-outcomes.mjs           # dry run
node --env-file=.env scripts/ops/repair-duplicate-outcomes.mjs --apply
```

Dry run first and read the output. It reports duplicate groups and
`InterventionThreshold` rows claiming more conversions than impressions.

The script does two things and **they must run together.** It folds the
duplicate outcome rows the §2.1 bug wrote, and it rebuilds the threshold
counters that same bug double-bumped. `skipImpressions` is over-counted by
roughly the number of skip conversions, which deflates skipCVR and **biases the
live sampler toward showing**. Repairing the rows without the counters leaves
the evidence table and the state table disagreeing, which is worse than the
consistent error it replaces.

Run it at low traffic — it rewrites counters the decision endpoint is writing
to concurrently. Only add `@@unique([shopId, aiDecisionId])` once it reports
zero duplicate groups.

`recordConversionForDecision`'s create path already catches P2002 and re-reads,
which is correct both before and after the index exists, so that follow-up
needs no second change.

### 5.2 Register the reversal webhooks

```
shopify app deploy
```

Required. Without it `orders/updated` and `orders/cancelled` never arrive,
recovered revenue can only go up, and the refund handling in §2.3 is dead code.
No scope change (`read_orders` already covers both), so no merchant re-auth.

This also ships the extension changes. Either order is safe — old carts carry
legacy stamps and resolve exactly as they do today — but note carts live about
14 days, so budget for a mixed-stamp period of at least that long.

## 7. Known gaps in what shipped

Recorded in the code as well, but collected here.

- **M3 is computed and not displayed.** The Verified Lift card still renders
  `getIncrementality` with its numerator fixed. Promote `metrics.m3` and retire
  `getIncrementality` when 09-19 §2.2 and §2.3 close — §2's own instruction is
  not to read a lift number before then.
- **M3's unit of analysis is the page load, not the visitor.** Both arms are
  intent-to-treat now, which is the right shape, but a holdout visitor is
  sticky and accumulates N decisions while a treated visitor accumulates a mix.
  Decisions-per-converting-visitor still differs by arm. `resparqVisitorId`
  exists; ITT should be per-visitor.
- **The legacy path still bills and reports on `total_price`** — `orderValue`,
  `updateAnalytics`, `storeConversion`. Commission is charged on a basis that
  includes sales tax while the M1 card excludes it. Reconcile before the next
  billing cycle.
- **`InterventionOutcome.revenue` changes basis mid-column** at `5d58ca0`, old
  rows `total_price` and new rows subtotal, with no generation marker. Record
  the cutover date before any cohort analysis reads the tax delta as a trend.
- **Untimestamped legacy render stamps fail open** on the §3.2 window bound.
  Timestamped stamps landed 2026-09-19, so carts predating that have no clock.
  A pre-09-19 cart can credit an order outside the window. Self-resolves as
  those carts expire, roughly 2026-10-04. Covered by a test that says so.
- **M4 is not on the merchant dashboard.** §2.5 calls it internal and
  diagnostic and it is — a tripwire for a silent confirm-render failure, aimed
  at us. A red banner telling a paying shop their install is broken, on a ratio
  ordinary causes depress, costs more trust than it saves. Read it from
  `scripts/dev/dashboard-preview.mjs`.
- **"Show rate" in the admin console is not a show rate.**
  `admin-metrics.server.js` defines it as `shown / (shown + skipped)`, which
  omits `missed` — decided-but-never-rendered — from both sides. It reads 100%
  for the live shop while the real render rate is 9/381 ≈ 2.4%. The number is
  internally consistent; the label is wrong. Not changed here.

## 8. Traps — additions to 09-19 §9

- **Production does not run migrations.** `prisma db push` at container boot.
  Anything you put in `prisma/migrations/` is for local and for
  migrate-managed environments only, and a schema change that `db push` cannot
  apply cleanly is an outage, not a failed deploy.
- **A cart carries stamps from many page loads, and Shopify never clears one.**
  Any reasoning of the form "the cart says X" has to say *which stamp* and
  *when*. Clearing is a fire-and-forget fetch; correctness must not depend on
  it landing.
- **Shopify clears a cart attribute with the empty string, not null.** A
  cleared stamp reads as present with a blank value unless normalised.
- **`current_subtotal_price` already has the refund in it.** Subtracting a
  reversal from it counts the refund twice.
- **Three of the four review rounds on this work found blockers in the
  *fixes*, not in the original code** — a boot loop, a double-subtracted
  refund, and an override that booked a merchant's own newsletter revenue as
  ours. Fixes to attribution logic are as likely to be wrong as the bug. Have
  them reviewed.
